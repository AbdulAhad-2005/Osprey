Platform Architecture: Request Flow, Graph, and Flexibility Analysis
1. REQUEST FLOW (end-to-end)
┌─────────────────────────────────────────────────────────────┐
│ ① USER / LLM INPUT                                          │
│   "probe morth.gov.in"                                       │
│   → AGENTS.md (behavioral rules + tool table)                │
│   → platform_skills (30 skill files, advisory only)          │
│   → platform_playbook (optional workflow suggestions)        │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ② TOOL INVOCATION                                           │
│   Typed: subfinder_scan, httpx_probe, nmap_syn_scan, ...    │
│   Generic: platform_exec(tool="subfinder_scan", params=...)  │
│   Custom: platform_script(code="...") / platform_shell()    │
│   Background: platform_job_start(kind="tool", tool=...)     │
│                                                              │
│   * additional_args = any valid CLI flags                    │
│   * params_json = domain/target/host/url auto-mapped         │
│   * force_refresh = bypass cache                             │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ③ KALI BACKEND EXECUTION                                    │
│   Tool binary runs (subfinder, httpx, nmap, python3, ...)   │
│   STDOUT + STDERR captured                                   │
│   Exit code, timeout, success/failure recorded               │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ④ INGEST RULES (ingest_rules.json) — 7 regex patterns       │
│                                                              │
│   Rule types:                                                │
│   ├─ subdomain_line    → subdomain finding                   │
│   ├─ open_port_line    → port finding (port/protocol/service)│
│   ├─ vendor_fingerprint_header → technology finding          │
│   ├─ console_or_app_path → url finding                       │
│   ├─ cors_star         → observation finding                 │
│   ├─ spa_catchall_suspect → observation (unverified)         │
│   └─ json_api_body     → observation (HIGH)                  │
│                                                              │
│   * Each rule: pattern, finding_type, evidence_grade,        │
│     claim_severity, title_template, tags                     │
│   * ONLY stdout matching these 7 patterns is "seen"          │
│   * Everything else is stored as "observation" (raw_output)  │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ⑤ FINDING STORAGE (platform_findings)                       │
│                                                              │
│   Each finding has:                                          │
│   ├─ id (UUID)                                               │
│   ├─ finding_type: subdomain|host|url|port|service|          │
│   │                 technology|observation                    │
│   ├─ evidence_grade: observed|inferred|unverified            │
│   ├─ claim_severity: none|info|medium|high|critical          │
│   ├─ confidence: hypothesis|likely|confirmed                  │
│   ├─ title + evidence (raw snippet)                          │
│   ├─ source_tool (which tool generated it)                    │
│   └─ tags (auto_ingest, subdomain, port, ...)                │
│                                                              │
│   * platform_record_finding() adds manual findings            │
│   * Raw tool stdout stored as "observation" even if unparsed │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ⑥ GRAPH CONSTRUCTION (implicit, not visible as API)          │
│                                                              │
│   Nodes created from findings (typed by finding_type):       │
│   ├─ subdomain → domain seed                                 │
│   ├─ host → IP node (resolves_to)                            │
│   ├─ url → host node (hosted_on)                             │
│   ├─ ip → port node (has_port)                               │
│   ├─ port → service node (runs)                              │
│   └─ technology → url/host node (detected_on)                │
│                                                              │
│   Edges are NAMED by the platform (not by me)                │
│   ├─ resolves_to, hosted_on, has_port, runs, detected_on     │
│   ├─ sisters (domain_hunter → sister linked)                 │
│   └─ seeds (from platform_set_target)                        │
│                                                              │
│   * Graph is queried via platform_graph_query()              │
│   * Filterable by asset_type + contains substring             │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ⑦ CONTEXT GENERATION (platform_context)                      │
│                                                              │
│   A. Crown Jewels (scored)                                   │
│      Uses thinking_model.json role_weights:                  │
│      patterns matched on hostname → weight assigned          │
│      + unique_tool_sources count                             │
│      + graph_edges count                                     │
│                                                              │
│   B. Open Loops (3 sources combined)                         │
│      ├─ tech_dispatch.yaml signal matching                  │
│      │   e.g. finding_type=url, min_count=3 →                │
│      │   "run waybackurls"                                    │
│      ├─ escalation_matrix.yaml fallback chains               │
│      │   e.g. subfinder empty → try amass → fierce → dnsenum │
│      └─ graph_pivots (structural gaps)                       │
│          e.g. ips_unscanned, hosts_no_http, sisters_unprobed │
│                                                              │
│   C. Coverage Gaps (advisory)                                │
│      surface_too_shallow, resolution_thin, etc.              │
│                                                              │
│   D. Attack Surface Tree (hierarchical)                      │
│      seed → subs → hosts → IPs → ports → services           │
│                                                              │
│   E. Inferred Focus (advisory)                               │
│      application_or_deeper, web_only_perimeter, etc.         │
└────────────────────┬────────────────────────────────────────┘
                     ↓
┌────────────────────┬────────────────────────────────────────┐
│ ⑧ OUTPUT TO LLM                                              │
│   Tool stdout + parsed findings + open loops + context        │
│   → LLM decides next action from open loops or invention      │
└─────────────────────────────────────────────────────────────┘
2. WHAT THE PLATFORM "SEES" (data model)
Dimension	Sees	Doesn't See
Tool output	Regex-matched patterns from 7 ingest rules	Full context, nuance, partial data, error messages
Relations	Predefined edge types (resolves_to, hosted_on, has_port, runs, detected_on, sisters, seeds)	Custom/ad-hoc relationships ("this API belongs to this app", "this host is a staging mirror")
Technology	Only HTTP headers matching vendor_fingerprint_header regex	JS framework detection from bundle analysis, custom headers, inferred stack from URL patterns
Severity	Only from regex match + claim_severity in ingest rules + platform_record_finding	True risk assessment, data sensitivity, business impact
Confidence	3 grades: observed/inferred/unverified — assigned by rule, not by reasoning	Contextual confidence (e.g., "port 443 open but content is weird → demote")
Score	Pattern weight + tool source count + edge count	Business context, attack path analysis, data criticality
3. CROWN JEWELS SCORING FORMULA
score = Σ(role_weights matching hostname)
      + (count of unique tool sources) * multiplier
      + (count of graph edges) * multiplier
Example from morth.gov.in = 364:

role business_portal (24) + admin_identity (32) + voice (30) = 86 from patterns
~15 unique tool sources → adds ~150
~30 graph edges → adds ~128

5. FLEXIBILITY & ADAPTABILITY COMPARISON (recon/network phases only)
Our Platform
Aspect	Our Platform
Tool selection logic	Config-driven (YAML/JSON). LLM reads outputs and picks from preset suggestions or open loops
Graph edge naming	Fixed set from ingest rules + platform_set_target. Cannot create custom relations
Finding correlation	Regex-based ingest rules only. No cross-finding correlation
Failure adaptation	escalation_matrix.yaml has static fallback chains per technique
Technology detection	1 ingest rule for HTTP headers. No JS/SPA analysis
Scoring	thinking_model.json role_weights (8 patterns). Static weights
Custom logic	platform_script (Python/bash). Runs outside the graph/scoring system
Parallelism	platform_job_start (max 4). LLM manages coordination
DarkMoon (pentest.md + signal detection matrix)
Aspect	DarkMoon
Tool selection logic	Agent-based orchestrator reads prior results → picks tool by context. Not config-driven
Graph edge naming	Signal Detection Matrix auto-tags tech → creates dynamic task chains. Not hardcoded
Finding correlation	Signal Detection Matrix has 14+ regex patterns for tech auto-classification. WordPress agent goes full killchain on match
Failure adaptation	Orchestrator agent suggests alternatives dynamically based on tool output type
Technology detection	14+ signal patterns in pentest.md (header analysis, path analysis, WAF detection, CMS detection)
Scoring	No centralized scoring — but per-agent assessment
Custom logic	Role-based agents (AD agent, WordPress agent) — each has full killchain for their domain
Parallelism	Agent decides parallel vs sequential
Why more flexible:

Signal Detection Matrix can classify any tech pattern and route to a specialized agent
Agent-based orchestration means tool choice adapts to context, not config files
Specialized agents (WordPress, AD) have bespoke workflows for their target
HexStrike (AI Decision Engine + 40+ tools)
Aspect	HexStrike
Tool selection logic	AI Decision Engine evaluates multiple tool paths → chooses optimal by probability of useful output
Graph edge naming	CVEIntelligenceManager correlates findings → creates vulnerability-domain relationships
Finding correlation	CVEIntelligenceManager maps discovered versions to CVEs and exploit availability
Failure adaptation	Decision tree with fallback probabilities — "if tool A fails, try B with {params}"
Technology detection	Tech detection → CVE correlation → exploit suggestion pipeline
Scoring	ML-based asset prioritization (proprietary)
Custom logic	Visual reporting dashboard, Redis-backed session persistence
Parallelism	Job batching across 40+ tools
Why more flexible:

AI Decision Engine evaluates probability-based tool chains, not static fallbacks
CVEIntelligenceManager connects findings to exploitability — adaptive correlation
ML scoring adapts to engagement data, not hardcoded patterns
Shannon Plugin (Sisyphus → Oracle → Librarian → Prometheus)
Aspect	Shannon Plugin
Tool selection logic	Multi-agent chain with escalating reasoning: Sisyphus (scout) → Oracle (analyze) → Librarian (research) → Prometheus (report)
Graph edge naming	Oracle agent infers relationships ("this endpoint calls that backend service")
Finding correlation	Librarian cross-references findings with public knowledge sources
Failure adaptation	Each agent type has different reasoning depth — automagic escalation on ambiguity
Technology detection	JS bundle analysis (main.*.js → extract API routes, keys, internal hosts)
Scoring	Not visible in plugin layer
Custom logic	Biz logic testing (Prometheus generates hypotheses about business function)
Parallelism	Linear chain (Sisyphus→Oracle→Librarian→Prometheus)
Why more flexible:

JS bundle analysis extracts APIs from SPAs dynamically (no hardcoded patterns)
Oracle infers business logic relationships (not just technical edges)
Agent escalation automates depth increases without config changes
Shannon Core (Temporal + 4-level proof scale)
Aspect	Shannon Core
Tool selection logic	Temporal durable workflows — stateful, retry-able, human-interruptible
Graph edge naming	White-box + black-box fusion — combines static analysis edges with dynamic findings
Finding correlation	4-level proof scale (speculative → plausible → probable → confirmed). Rigorous evidence grading
Failure adaptation	Temporal automatically retries with backoff, alternative paths, human-in-loop
Technology detection	White-box (source/configuration parsing) + black-box (browser/API) combined
Scoring	4-level proof scale with narrative evidence chain
Custom logic	Durable workflow engine — any custom logic as code, not config
Parallelism	Temporal workflow branching — native parallel/recovery
Why more flexible:

Durable workflows mean state is preserved across failures — can resume mid-scan
White-box + black-box fusion detects tech from source code, not just network responses
4-level proof scale enforces evidence hygiene that adaptive scoring lacks
6. SUMMARY: THE CORE GAPS
Gap	Our Platform	External Tools
Graph edge flexibility	6 fixed edge types from ingest	Shannon Oracle infers biz logic edges; DarkMoon Signal Matrix creates by tech; HexStrike CVEIntelligence correlates vulns
Technology detection depth	1 regex rule for HTTP headers	DarkMoon 14+ patterns; Shannon JS bundle extraction; HexStrike version→CVE pipeline
Tool selection	Config-driven + LLM picks from open loops	DarkMoon agent-driven; HexStrike AI probability eval; Shannon agent escalation; Temporal durable workflows
Failure adaptation	Static fallback chains in YAML	DarkMoon dynamic by context; HexStrike probability-weighted; Shannon auto-escalates; Temporal auto-retry
Finding correlation	None — findings are independent nodes	DarkMoon full killchain per tech; HexStrike CVE→exploit; Shannon proof scale chains evidence
Custom relations	Can't name them — only ingest/record	Shannon Oracle names relations dynamically; HexStrike correlates across domains
The root issue: Our platform is a config-driven orchestration engine — all behavior is predefined in YAML/JSON configs. The external tools (especially Shannon and HexStrike) are agent-driven reasoning engines — they infer, correlate, and adapt dynamically based on what they find. Config gives us consistency, but cognition gives them flexibility.
