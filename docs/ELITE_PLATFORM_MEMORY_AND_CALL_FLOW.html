Memory, graph, platform tools, and complete engagement call flow

A technical report explaining where the platform remembers information, how a relational database represents the graph, what every platform_* function actually does, what the LLM can author, what the platform computes, and how a call travels from OpenCode through MCP and FastAPI into execution, findings, graph, recall, and reporting.

We do not hardcode the engagement. The platform supplies a lab, durable evidence, a shared notebook, and a referee. The LLM chooses the question, experiment, interpretation, relation, and stopping point.

1. How platform memory actually works

The answer is not “everything is in PostgreSQL.” Durable analytical memory is primarily relational PostgreSQL, but execution output also lives in the Kali filesystem and several operational features currently live only in backend process memory.

Durable

PostgreSQL

Engagements, runs, findings, asset nodes, asset edges, and latest tool coverage.

This is the strongest “fat memory” layer today.

Container filesystem

Kali artifacts

Script files, stdout/stderr files, and fallback output artifacts under an engagement workdir.

Persistent only while the container or mounted volume survives.

Process-local

Operational state

Jobs, context snapshots, recent stdout index, execution cache, and audit events.

A backend restart currently clears these.

Conversation

LLM context

Current reasoning and narrative that has not been explicitly written back.

Not platform memory until a write API or parser persists it.

1.1 PostgreSQL is tabular

PostgreSQL stores rows and columns. Flexible fields such as tags and metadata are currently serialized into text columns containing JSON. The platform reconstructs typed Pydantic objects when rows are read.

TablePurposeImportant identityDurability
engagements Target, name, status, rules of engagement, counters, timestamps. 12-character engagement ID. PostgreSQL
findings Evidence, inferences, hypotheses, tags, graph-link audit findings, operator notes. Random 12-character finding ID; every row has engagement and run IDs. PostgreSQL
asset_nodes Graph vertices such as host, URL, IP, port, service, and technology. Composite key (engagement_id, asset_type:lowercase_label). PostgreSQL
asset_edges Directed graph relationships. Unique engagement + source + target + relationship. PostgreSQL
tool_coverage Latest success/finding count for one tool and asset; feeds gaps and attempts. Unique engagement + tool + asset; repeats overwrite. PostgreSQL
Artifact files Large stdout/stderr and script output. Path under /tmp/pentest/<engagement>/. Kali filesystem
Jobs/delta/index/cache Parallel task state, last context counts, recent artifact paths, cached responses. Python dictionaries/deques keyed by engagement or job. Process-local

1.2 A finding is the universal evidence record

Findings are not only vulnerabilities. A finding can represent a hostname, URL, port, service, technology, raw observation, operator hypothesis, graph-link explanation, or asset tag audit record. This is why the findings table acts as the platform’s shared notebook. 

Finding
├── identity: id, engagement_id, run_id, created_at
├── classification: finding_type, confidence, evidence_grade, claim_severity
├── narrative: title, description, evidence, raw_data, notes
├── origin: source_tool, target
└── flexible structure: metadata_json, tags_json, extra_json
Durability nuance Evidence grade and claim severity are mirrored into extra_json rather than dedicated SQL columns. The Pydantic model hydrates them on read and enforces the severity ceiling.

1.3 Engagement scope is the memory boundary

MCP keeps an active engagement_id, run_id, and seed target. Normal memory calls inject the engagement ID automatically. Findings and graph queries are engagement-scoped, so the same hostname in two engagements creates separate graph records. A run is an audit/session stamp; most recall intentionally reads engagement-wide memory.

2. How a graph is stored in tabular PostgreSQL

A graph does not require a graph database. This platform uses an adjacency-list pattern: one table stores vertices and another stores directed edges. SQL reconstructs neighborhoods by matching edge source and target IDs to node IDs.

2.2 Operator-authored graph links

platform_graph_link lets the LLM supply a business relation that the generic parser could not know. The platform normalizes syntax and decides whether the relation must be marked as a hypothesis. 

platform_graph_link(
  source="host:portal.example.com",
  target="host:api.example.com",
  relation="calls_backend_api",
  evidence="Observed API base in main.js and a matching JSON response",
  evidence_grade="observed",
  derived_from="routeFinding,responseFinding"
)

One call performs two related writes:

  1. Upsert source and target nodes, then add a directed edge.
  2. Create a finding that stores evidence, grade, relation metadata, and parent IDs.
asset_edges:
host:portal.example --calls_backend_api--> host:api.example

findings:
REL host:portal.example --calls_backend_api--> host:api.example
metadata = {
  source_id, target_id, relationship,
  edge_kind: "asserted",
  derived_from: ["routeFinding", "responseFinding"]
}
Why the finding is necessary The current edge table has only source, target, relationship, and engagement. Evidence and grade therefore live in the companion finding rather than directly on the edge.

5. What the LLM can add, what is hardcoded, and what is assistive

The design separates cognition from invariants. “Config-driven” does not mean the LLM owns safety. “Hardcoded” is acceptable for structural invariants and safety, but not for deciding the next engagement step.

LLM-authored

Meaning and experiments

  • Which uncertainty matters next.
  • Tool and target parameters.
  • Additional valid CLI arguments.
  • Custom Python/Bash probes.
  • Finding markers and evidence snippets.
  • Relation names and source/target assets.
  • Asset roles, reasons, and bounded boost.
  • Hypotheses, plans, and confirmation strategy.
  • derived_from evidence parents.
  • Explicit fanout shortlist.
  • Final narrative and stopping decision.
Platform-enforced or structural

Invariants and bounds

  • Engagement-scoped persistence.
  • Finding and asset type enums.
  • Evidence grade values.
  • Severity ceiling by grade.
  • Relation syntax normalization.
  • hypothesis_ for non-observed links.
  • Node/edge identity rules.
  • Shell binary allowlist and syntax restrictions.
  • Parameter and timeout bounds.
  • Fanout confirmation.
  • Finalize claim-integrity checks.
Assistive only

Signals, not orders

  • Open gaps.
  • Coverage gaps and inferred focus.
  • Technology dispatch signals.
  • Thinking cards.
  • Playbooks and skills.
  • Background-job suggestions.
  • Correlation hypotheses.
  • Crown-jewel scores.
  • Attempt state.
  • Report outline structure.

6. Complete engagement lifecycle

An engagement is both the authorization/memory scope and the key injected into almost every backend request. The LLM does not manually pass it after binding.

6.1 Binding

  1. User supplies a full domain or short name.
  2. platform_set_target calls target analysis with DNS probing.
  3. Ambiguous short names return candidates; the LLM must ask the user.
  4. A confirmed domain resolves or creates an engagement.
  5. MCP stores active target, engagement ID, and run ID in its session process.
  6. Switching target rotates the active session and warns that previous chat evidence belongs to another engagement.

6.2 Orientation

platform_context calls the adaptive context endpoint, which assembles:

findings summary
+ graph summary and condensed attack-surface tree
+ network surface
+ coverage gaps and open loops
+ crown-jewel ranking
+ thinking cards
+ current process-local jobs
+ recent process-local artifact index
+ context count delta
+ finalize readiness

This packet informs the LLM. It does not execute a stage. The LLM may use a typed tool, generic catalog execution, shell, script, job, or write API.

7.1 Example call

platform_exec(
  tool="httpx_probe",
  params_json={"target": "api.example.com"},
  additional_args="-title -status-code -tech-detect",
  timeout_seconds=90,
  force_refresh=false
)

7.2 MCP layer

  1. Accepts params_json as an object or JSON string.
  2. Requires an active engagement.
  3. Clamps timeout.
  4. Injects engagement ID, run ID, cache flags, recovery flag, and record_findings=true.
  5. POSTs to /api/v1/mcp/execute.

7.3 Backend execution service

  1. Resolve tool registry definition and aliases.
  2. Resolve engagement/run and seed target.
  3. Evaluate governance.
  4. Merge typed parameters with additional_args.
  5. Map aliases such as target/domain/host/url to the tool’s primary parameter.
  6. Reject blocked shell-control characters in catalog string parameters.
  7. Validate required values and scan-budget constraints.
  8. Compute engagement-scoped cache key.
  9. On cache miss, build command and execute inside Kali.

7.4 Memory promotion

The returned stdout/stderr follows multiple paths:

Kali stdout/stderr
├── registered deterministic parser
├── free-form parser when appropriate
├── universal YAML ingest rules
├── relation marker parser
├── fallback raw observation when unparsed
└── artifact/index recording
  1. Findings are normalized and severity-clamped.
  2. Findings are written to PostgreSQL.
  3. Supported finding types are projected into nodes/edges.
  4. Correlation scans current findings and may add hypothesis links/tags.
  5. Latest tool coverage is upserted.
  6. Engagement counters update.
  7. Successful non-empty result may enter process-local cache.

7.5 Return to LLM

MCP formats success, return code, timeout, cache, command, bounded stdout/stderr previews, top finding titles, artifact paths, and current open gaps. The LLM then interprets the evidence and chooses whether to deepen, pivot, annotate, or stop.

8. Walkthrough: writing cognition and evidence

Chat reasoning is not durable by default. These calls move selected cognition into shared engagement memory.

8.1 Store an observed fact

platform_record_finding(
  title="https://api.example.com/v1/users returned user records",
  evidence="HTTP/1.1 200 OK; Content-Type: application/json; {…}",
  finding_type="url",
  evidence_grade="observed",
  claim_severity="high",
  derived_from="routeDiscoveryFinding"
)
  1. MCP injects engagement and run IDs.
  2. FastAPI validates the finding model.
  3. Severity is clamped: observed permits up to critical, so high remains high.
  4. Finding store writes PostgreSQL.
  5. Finding endpoint graph-projects the URL, host, and hosted_on relation.
  6. The returned finding ID can support later relations and claims.

8.2 Store a hypothesis

platform_think(
  hypothesis="Portal and admin may share session validation",
  evidence="Both set Domain=.example.com",
  plan="Replay one valid session against both applications"
)

This writes an unverified, hypothesis-confidence, severity-none observation. It does not create a graph edge because the relation has not yet been asserted.

8.3 Store a semantic relation

platform_graph_link(
  source="host:portal.example.com",
  target="host:admin.example.com",
  relation="shares_session_validation",
  evidence="The same authenticated cookie was accepted by both hosts",
  evidence_grade="observed",
  derived_from="cookieFinding,replayFinding"
)

The graph edge represents topology/meaning. The companion relation finding holds the evidence and evidence-chain parents.

8.4 Tag priority

platform_tag_asset(
  asset="host:api.example.com",
  role="sensitive_data_backend",
  boost=35,
  reason="Observed endpoint returns customer account data"
)

The node receives operator metadata and the findings table receives an inferred audit row. Crown-jewel ranking reads both; the current double-counting bug is scheduled for repair.

9.2 Parser outcomes

10. Walkthrough: background jobs and parallel branches

Jobs let the LLM keep reasoning while a slow tool, shell command, or script runs. Today they are real concurrent asyncio tasks but are not durable orchestration records. 

platform_job_start(
  kind="tool",
  tool="amass_scan",
  params_json={"domain": "example.com"},
  label="Independent subdomain source",
  timeout_seconds=900,
  reason="Test whether initial inventory is source-biased"
)
  1. MCP validates kind and required payload.
  2. Backend checks running count against parallelism.yaml.
  3. It creates job_<12 hex> in a Python dictionary.
  4. asyncio.create_task starts the normal tool/shell/script service.
  5. Underlying execution writes findings and graph automatically.
  6. The LLM continues another branch.
  7. platform_job_poll reads state.
  8. platform_job_result reads the stored response after completion.

What is already parallel

Independently started jobs can run concurrently up to the configured per-engagement cap.

What is not parallel

platform_fanout and platform_fanout_assets currently await each asset sequentially.

Restart and cancellation limitation Job records, tasks, and result payloads are process-local. There is no cancellation endpoint, heartbeat, durable lease, partial-output API, or startup reconciliation yet.

11. Walkthrough: recall, evidence chain, and final report

11.1 Search before repeating

platform_memory_search(query="Set-Cookie")
platform_attempts(asset="api.example.com")
platform_graph_query(asset_type="host", contains="api")

Search finds textual memory, attempts shows latest coverage state, and graph query returns matching assets with incident relations. None of these calls writes or bans a rerun.

11.2 Trace one claim

platform_evidence_chain(finding_id="8ab314df90c2", depth=4)

The service loads engagement findings, walks derived_from parents recursively, and finds direct children citing the root. It returns structure only; evidence grade does not automatically propagate.

11.3 Verify stored findings

platform_findings(limit=200)
platform_crown_jewels(limit=15)

The LLM should distinguish direct evidence from inference and use ranking only to prioritize attention.

11.4 Finalize

platform_finalize_check()
platform_report_outline()

Finalize checks:

  • HIGH/CRITICAL claims whose grade is not observed.
  • Weak critical/CVE evidence.
  • SPA/HTML false-API claims.
  • Optional hypothesis-only attack paths.
  • Thin structured memory and coverage gaps.
  • Cumulative port-flood signals.

Strong observed impact can waive infrastructure completeness noise, but claim-integrity blockers remain. The outline then groups memory; the LLM authors the prose.

12. Important current limitations

These are implementation truths, not design aspirations. They explain where the current platform behaves differently from the target architecture.

Memory durability

  • Jobs, deltas, stdout index, cache, and audit are process-local.
  • Artifacts can disappear with Kali /tmp.
  • Tool coverage overwrites repeat attempts.
  • Finding duplicates can accumulate.

Graph fidelity

  • Service and technology nodes are disconnected.
  • URL/IP canonicalization is limited.
  • Edges do not directly store provenance.
  • Graph query is filtering, not traversal.

Execution reliability

  • Fallback artifacts can contain already-capped output.
  • Artifact framing can produce malformed reads.
  • Nmap custom ports can be silently ignored.
  • Fanout batching is sequential.

Intelligence and policy

  • Correlation lacks source finding IDs.
  • Operator boost can be counted twice.
  • SPA classification is whole-output scoped.
  • Registered-tool governance is currently permissive.
